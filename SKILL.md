# Oracle Database Silent Install on Linux

## Overview

Deploy Oracle Database on RHEL-family Linux with a staged, reviewable,
parameterized workflow. The design goal is repeatability and safety: read-only
preflight, root steps explicitly delegated to the human, response files generated
from templates with no hardcoded secrets, and a final verification gate before
any cleanup.

Distilled from a real 19c deployment on CentOS 7.9 (non-CDB single instance,
SGA 512M / PGA 256M, local-only listener). `references/` carries the
version-specific detail; this file carries the orchestration.

## When not to use this skill

Not a fit for: production HA topologies (RAC, Data Guard, ASM), Windows targets,
container/docker builds, or any deployment where an existing database must be
upgraded in place. Say so and stop, rather than stretching the workflow.

## Golden Rules (non-negotiable)

1. **Read-only before write.** Never run `mkdir`, `chown`, `yum`, `sysctl -w`,
   `unzip`, or an installer until a read-only preflight has been reported and the
   user has confirmed the plan.
2. **Root steps belong to the human.** Output exact root command blocks for the
   user to run in a root session; wait for their confirmation before continuing.
   Do not request or accept a root password into the conversation.
3. **Never expose key material.** SSH key files are used read-only and implicitly
   by the SSH client. Never display, copy, transmit, or quote key contents,
   fingerprints, or Base64 fragments — not in chat, logs, reports, or artifacts.
4. **Secrets stay on the target host.** SYS/SYSTEM/PDBADMIN passwords are filled
   interactively by the user via `scripts/fill_dbca_passwords.sh`. Never place a
   real password in a response file generated by an agent, in a command line, or
   in any output. Response files hold `__CHANGE_ME_*__` placeholders until the
   user fills them.
5. **Stage gates.** Stop at each checkpoint and wait for user confirmation. Do not
   run `dbca` until `runInstaller` and the root scripts are verified.
6. **Cleanup is last and surgical.** Only delete the install ZIP after full
   verification passes, and only that single file. Never `rm -rf` an `oradata`
   directory.

## Workflow Decision Tree

Before generating any plan, resolve these four parameters with the user (decision
data in `references/version-matrix.md`):

| Parameter | Choices | Default for local testing |
|---|---|---|
| Version | 11gR2 / 12c / 18c / 19c | 19c |
| OS platform | OL / RHEL / CentOS / Rocky / Alma, major version | CentOS 7.9 |
| Instance shape | non-CDB single instance / CDB+PDB | non-CDB single instance |
| Memory profile | minimal / balanced / production | minimal (SGA 512M, PGA 256M, processes 100) |

**Hard blocker check first.** On 19c/18c/12.2+, verify `GLIBC_2.14` exists
(`scripts/precheck.sh` reports `GLIBC_2.14_symbols`). RHEL 6 / glibc 2.12 cannot
run these binaries at all — stop and recommend a 7+ OS rather than attempting
`-ignorePrereq`. 11g tolerates older glibc.

**Unsupported-but-workable OS** (CentOS instead of OL/RHEL): use
`CV_ASSUME_DISTID=OL7` (or the matching major) plus `-ignorePrereqFailure` /
`-ignorePreReqs`. Warn the user that the platform is outside Oracle support and
record it in the plan.

## Staged Workflow

### Stage 0 — Preflight (read-only)

Run `scripts/precheck.sh` on the target. For an SSH alias:

```bash
ssh <alias> 'bash -s -- 19c' < scripts/precheck.sh
```

Report: OS/glibc, CPU/memory/disk/inode, hostname resolution, users/groups,
missing RPMs, kernel parameters, limits, security settings, install ZIP location,
and any `BLOCKER:` lines. Resolve blockers before planning.

### Stage 1 — Plan and confirmation

Generate the review sheet rather than writing one by hand:

```bash
HOST_ALIAS=<alias> VERSION=19c bash scripts/show_plan.sh 19c > /tmp/plan.txt
```

Present it. It carries the directory tree and space budget
(`references/planning.md`), the exact parameter values, the split of root steps
(user) versus oracle steps (agent), and every checkpoint. Add explicit acceptance
of any risk (unsupported OS, tight memory, warning-only package). Wait for
explicit approval.

### Stage 2 — System preparation (user executes)

```bash
bash scripts/gen_root_prep.sh 19c > /tmp/root_prep.sh   # prints, never executes
```

Review it, then hand the user the block to run as root: groups (`oinstall`,
`dba`, `oper`), user/group membership, directory creation and ownership,
`/etc/hosts` FQDN mapping to a non-loopback IP, `/etc/sysctl.d/99-oracle.conf`,
limits, and missing packages. Command templates: `references/planning.md`.

Validate the reported results. Note that `getent hosts` can show `::1` even when
`hostname -f` and `getent ahosts` are correct — judge by `hostname -f` and
`ping $(hostname)`, not by `getent hosts` alone.

### Stage 3 — Software install (oracle user)

1. Environment:

```bash
bash scripts/gen_env_file.sh - 19c | tee -a /home/oracle/.bash_profile
source /home/oracle/.bash_profile
```

2. Unzip the image-based 19c/18c/12c zip **directly into the empty ORACLE_HOME**
   as the oracle user. 11g uses a different layout — see
   `references/version-matrix.md`.

3. Generate the response file, then install:

```bash
bash scripts/gen_db_install_rsp.sh "$ORACLE_HOME" /home/oracle/db_install.rsp 19c
cd "$ORACLE_HOME"
./runInstaller -silent -responseFile /home/oracle/db_install.rsp \
  -ignorePrereqFailure -waitforcompletion
```

Confirm `Successfully Setup Software` and capture the two root script paths.

### Stage 4 — Root scripts (user executes)

Hand over the exact paths printed by runInstaller, typically
`/u01/app/oraInventory/orainstRoot.sh` then `$ORACLE_HOME/root.sh`. Verify
afterwards: `/etc/oratab` entry exists, `root.sh` log has no errors, `sqlplus -V`
works under the oracle environment.

### Stage 5 — Listener and database (oracle user)

1. Listener — the 19c template lives at
   `$ORACLE_HOME/assistants/netca/netca.rsp`, **not** `install/response/`:

```bash
netca -silent -responsefile "$ORACLE_HOME/assistants/netca/netca.rsp"
```

2. For local-only testing, bind loopback instead of the netca default (which
   follows the FQDN and exposes 1521 on the LAN):

```bash
TNS_OUT="$ORACLE_HOME/network/admin/tnsnames.ora" \
  bash scripts/gen_listener_ora.sh "$ORACLE_HOME/network/admin/listener.ora"
lsnrctl reload
ss -lntp | grep 1521     # expect 127.0.0.1:1521 only
```

3. Database: generate the response file, then **hand control to the user** to fill
   passwords in their own terminal:

```bash
bash scripts/gen_dbca_rsp.sh /home/oracle/dbca.rsp 19c
bash scripts/fill_dbca_passwords.sh /home/oracle/dbca.rsp   # expects: Remaining placeholders: 0
dbca -silent -createDatabase -responseFile /home/oracle/dbca.rsp -ignorePreReqs
```

If startup fails with `ORA-00838`, SGA is below the practical floor: raise it to
640M in the rsp and recreate, or alter it after startup.

### Stage 6 — Verification and cleanup

```bash
ssh <alias> 'bash -s -- <SID> 19c' < scripts/verify.sh
```

Require all of: instance OPEN, `IS_CDB` matches the plan, charset matches,
SGA/PGA/processes match, listener bound as intended, `tnsping` OK. Only then
delete the install ZIP as a single file and report final free space.

## Scripts

| Script | Purpose | Side effects |
|---|---|---|
| `scripts/precheck.sh` | Read-only readiness survey | None |
| `scripts/verify.sh` | Read-only post-install verification | None |
| `scripts/show_plan.sh` | Print the staged plan, tagged AGENT/ROOT/ORACLE | None |
| `scripts/gen_root_prep.sh` | Print the root preparation block | None |
| `scripts/gen_env_file.sh` | oracle user environment block | One file |
| `scripts/gen_db_install_rsp.sh` | Software install rsp from the media template | One file |
| `scripts/gen_dbca_rsp.sh` | CDB/non-CDB dbca rsp with placeholders | One file |
| `scripts/gen_listener_ora.sh` | Loopback listener.ora (+ tnsnames.ora) | One or two files |
| `scripts/fill_dbca_passwords.sh` | Interactive, no-echo password fill | Edits one file |

All scripts are standalone — stream the read-only ones over SSH with
`bash -s -- args`.
