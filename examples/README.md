# Examples

Two profiles that differ in the places where Oracle versions actually differ.
Both are generated by the scripts in `../scripts`, so they double as regression
fixtures: if a generator changes behaviour, these files change with it.

| Profile | Version | Shape | Demonstrates |
|---|---|---|---|
| `19c-minimal-centos79/` | 19c | non-CDB single instance, SGA 512M, loopback listener | the full seven-stage walkthrough and every artifact type |
| `11g-legacy-rhel6/` | 11gR2 | non-CDB single instance | legacy response-file keys, no CDB vocabulary, older glibc floor |

## Side-by-side: the one difference that bites

```
# 19c  ->  initParams carries the memory settings
initParams=sga_target=512M,pga_aggregate_target=256M,processes=100
automaticMemoryManagement=FALSE

# 11g  ->  dedicated keys, and no CDB keys at all
sgaTarget=800
pgaAggregateTarget=400
processes=150
automaticMemoryManagement=FALSE
```

Feeding the 11g form to a 19c `dbca` produces
`cvc-complex-type.2.4.a: Invalid content was found starting with element
'memoryType'` and stops the run. `gen_dbca_rsp.sh` branches on version so you
never have to remember which form goes where.

## Regenerating

```bash
cd 19c-minimal-centos79
set -a; . ./parameters.env; set +a
bash ../../scripts/gen_env_file.sh bash_profile.block "$VERSION"
bash ../../scripts/gen_root_prep.sh "$VERSION" > root_prep.sh
bash ../../scripts/gen_dbca_rsp.sh dbca.rsp "$VERSION"
TNS_OUT=tnsnames.ora bash ../../scripts/gen_listener_ora.sh listener.ora
bash ../../scripts/show_plan.sh "$VERSION" > "plan-$VERSION.txt"
```

`db_install.receipt` is *not* regenerated this way: a real install response file
starts from the template shipped inside the Oracle media
(`$ORACLE_HOME/install/response/db_install.rsp`), which this repository does not
redistribute. The receipt was produced against an equivalent template and its
paths normalised to this example's layout.
